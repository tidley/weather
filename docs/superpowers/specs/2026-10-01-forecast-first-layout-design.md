# Forecast-First Layout Design

## Purpose

Make the hourly forecast the first useful content on both desktop and mobile. The
page must show the key session decision data without allowing summary panels to
push the forecast below the initial viewport.

## Scope

Replace the current large decision panel and prominent best-windows card at the
top of the page with a compact status rail. Keep the existing forecast data,
scoring rules, location switcher, settings, and forecast interactions.

## Layout

The header remains compact and contains the location name, data update time,
location switcher, and settings control.

Immediately below it, a status rail presents the selected forecast period's:

- overall verdict and KI score
- average wind, gust peak, and wind direction
- tide usability
- next suitable session window

On wide screens, the rail is one horizontal row. On narrow screens, it wraps
into compact, readable segments without hiding critical metrics. It does not
use large cards, decorative space, or a separate hero section.

The existing 48-hour forecast follows directly after the status rail and is the
first large content block. It keeps its sticky row labels and horizontal scroll
on narrow screens. The visible table groups retain wind, gusts, direction,
temperature, rain, and sky information so a user can scan all core weather
conditions quickly.

Best windows, the main issue and tip, and the colour key move below the forecast
table. They remain available but no longer delay access to the forecast.

## Data Flow

The rail reuses the current summary values already calculated in `app.js`. No
API request, cache key, forecast calculation, or scoring threshold changes.
The best-window content remains generated by the current renderer and is only
repositioned in the document.

## Responsive Behaviour

Desktop uses a single concise row with dividers between metrics. Mobile stacks
or wraps rail segments while retaining the verdict, wind, gust, direction, and
tide values within the initial viewport. The forecast table stays horizontally
scrollable and preserves its existing sticky label column.

## Error Handling

Existing loading placeholders and unavailable-data dashes continue to render in
the compact rail. Reordering content does not add new failure states.

## Verification

- Confirm the forecast is visible below the header and status rail at desktop
  and mobile viewport sizes.
- Confirm all current summary values still update after a location change or
  refresh.
- Confirm the forecast table can still scroll horizontally on mobile and sticky
  labels remain legible.
- Run the available application checks and inspect desktop and mobile browser
  screenshots.
